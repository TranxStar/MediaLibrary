## 1. 项目概述

### 1.1 使用场景

学校活动视频剪辑的素材管理。典型工作流：

```
活动结束 → 从相机/手机导出几百个文件 → 拖进本软件
        → 软件自动统一格式、统一命名、生成缩略图
        → 剪辑时打开软件，靠缩略图和悬浮预览快速挑素材
        → 双击打开文件丢进剪辑软件
```

### 1.2 需求清单（含已确认决策）

| # | 需求 | 决策 |
|---|---|---|
| R1 | 界面简洁，打开即见文件缩略图 | 虚拟化网格首屏 |
| R2 | 视频悬浮播放 + 可拖进度 | LibVLC 直播源文件，无需代理 |
| R3 | 音频悬浮自动播放 | 同上，音频模式 |
| R4 | 双击打开文件 | ✅ 打开**库内** H.265 文件；右键另提供"打开原始文件" |
| R5 | 拖入即真实复制进库 | **转码后落盘**，库里是实体文件 |
| R6 | 统一为 H.265 | ✅ 已确认 |
| R7 | 照片统一为 PNG | ✅ 已确认（接受体积） |
| R8 | 音频保留原格式 | ✅ 已确认，仅复制不转码 |
| R9 | 命名 = 最内层文件夹名 + 独立序号 | ✅ `开幕式_001.mp4` |
| R10 | 原素材库外原位不动 | ✅ 已确认，零改动 |

### 1.3 明确的非目标（本期不做）

- ❌ 多用户 / 局域网共享 / 云端同步
- ❌ 时间线剪辑功能（本软件只管素材，不做剪辑）
- ❌ 移动端 / Web 版
- ❌ AI 自动打标签、人脸识别（未来可扩展）
- ❌ 素材库跨盘符分片存储

## 2. 技术选型

### 2.1 结论

| 层 | 选型 | 理由 |
|---|---|---|
| UI | **WPF** | LibVLCSharp 集成最成熟；VS2026 设计器完整；虚拟化方案成熟 |
| 框架 | **.NET 10 (LTS)** | SDK 10.0.203 已装；.NET 8 将于 2026-11 结束支持 |
| 播放 | **LibVLCSharp.WPF** | 解码能力 = VLC，ProRes/DNxHR/MXF 全能播，免转码 |
| 视频 | **FFmpeg 8.1.3** | 转码 H.265 + 抽帧；随包分发。⚠️ **9.0.2 的 NVENC 在你的驱动(596.36)上不可用**，详见阶段0报告 §2 |
| 图片 | **FFmpeg**（复用，不再引入 Magick.NET） | ✅ 阶段0实测：ffmpeg 能读 HEIC、能自动应用 EXIF 方向 → 省 24 MB 原生库和一个依赖 |
| 数据库 | **SQLite + Dapper** | 几百文件规模，轻量、零配置、单文件 |
| MVVM | **CommunityToolkit.Mvvm** | 源生成器，无反射开销 |

### 2.3 照片处理选型 —— 已由阶段0实测推翻初版结论

> ⚠️ **本节初版结论已作废。** 初版写的是"ffmpeg 缺 libheif 所以读不了 HEIC，必须用 Magick.NET"。
> 阶段0 实测证明**这个判断是错的**，实测证据见 `阶段0验证报告.md` §5。

**当初错在哪**：只 grep 了 demuxer 列表找 `heif`，没找到就下了结论。
实际原因是 **HEIF 与 MP4 同为 ISOBMFF 容器** —— ffmpeg 直接用
`mov,mp4,m4a,3gp,3g2,mj2` demuxer 就解开了，根本不需要专门的 heif demuxer。

**实测证据：**
```
$ ffprobe sample1.heic
codec_name=hevc  width=1440  height=960  nb_frames=1
format_name=mov,mp4,m4a,3gp,3g2,mj2

$ ffmpeg -i sample1.heic -frames:v 1 out.png     → 成功，2536 KB，1440x960
$ ffmpeg -i 竖拍测试.jpg -frames:v 1 out.png     → 900x1600，EXIF 方向已自动应用
```

**能力对照：**

| 能力 | ffmpeg | Magick.NET |
|---|---|---|
| 读 HEIC（含网格分块） | ✅ | ✅ |
| 自动应用 EXIF 方向 | ✅ 900x1600 | ✅ 900x1600 |
| HEIC → PNG | ✅ | ✅ |
| 额外体积代价 | 0（本来就要打） | **+24 MB 原生库** |

**最终选型：全部用 ffmpeg。**

| 任务 | 工具 |
|---|---|
| 视频转码 / 抽帧 / 波形 | ffmpeg（硬件编码，无可替代） |
| 照片 HEIC/JPEG/TIFF/WebP → PNG | ffmpeg（`-map 0:v:0` 显式取主图） |
| EXIF 元数据 → 数据库 | MetadataExtractor（纯托管，轻量） |

> **保留退路**：`MediaLibrary.Core` 里的 `IImageConverter` 抽象不变。
> 万一实际使用中遇到 ffmpeg 读不了的图片格式，把 Magick.NET 加回来即可，**不需要改动核心管线**。

### 2.4 二进制分发

```
MediaLibrary.App/
└─ Tools/
   ├─ ffmpeg.exe     ← ffmpeg 8.1.3 win64-gpl (BtbN)
   └─ ffprobe.exe
```
- 随程序打包，用户无需安装任何东西
- **构建时锁定具体版本号**并记录 SHA-256，避免上游变更导致行为漂移
- 来源：`https://github.com/BtbN/FFmpeg-Builds/releases/download/latest/ffmpeg-n8.1-latest-win64-gpl-8.1.zip`
  （实测下载 184 MB / 24 秒 / 7.7 MB/s）

#### ⚠️ 必须做的体积优化：libvlc 默认会塞进三个 CPU 架构

`VideoLAN.LibVLC.Windows` 的 targets 逻辑是"`Platform` 为 `AnyCPU` 时三套全开"，
而 `AnyCPU` 是 .NET 项目的默认值。**实测输出 325 MB，其中 193 MB 是无用的 x86/arm64。**

| 架构 | 大小 |
|---|---|
| win-x64 | 106.4 MB ← 只有这个有用 |
| win-x86 | 103.1 MB ← 无用 |
| win-arm64 | 89.7 MB ← 无用 |

**在 csproj 里显式关闭：**

```xml
<VlcWindowsX64Enabled>true</VlcWindowsX64Enabled>
<VlcWindowsX86Enabled>false</VlcWindowsX86Enabled>
<VlcWindowsArm64Enabled>false</VlcWindowsArm64Enabled>
```

**实测效果：325.3 MB → 132.5 MB。**

## 4. 数据模型

### 4.1 完整 Schema

```sql
-- ============ 元信息 ============
CREATE TABLE SchemaInfo (Version INTEGER NOT NULL);

-- ============ 素材主表 ============
CREATE TABLE Assets (
  Id            INTEGER PRIMARY KEY AUTOINCREMENT,
  Kind          TEXT    NOT NULL,           -- Video | Photo | Audio
  FileName      TEXT    NOT NULL,           -- 库内文件名：开幕式_001.mp4
  FolderKey     TEXT    NOT NULL,           -- 归一化相对目录：运动会/开幕式（根为 ''）
  LibraryPath   TEXT    NOT NULL,           -- 相对库根：运动会/开幕式/开幕式_001.mp4
  SourcePath    TEXT        NULL,           -- 原始来源绝对路径（可能已失效）
  SourceFolder  TEXT        NULL,           -- 拖入时最内层文件夹名：开幕式
  SizeBytes     INTEGER NOT NULL DEFAULT 0,
  QuickHash     TEXT    NOT NULL,           -- XxHash64(size|head64K|tail64K) 十六进制
  Width         INTEGER     NULL,
  Height        INTEGER     NULL,
  DurationMs    INTEGER     NULL,
  VideoCodec    TEXT        NULL,
  AudioCodec    TEXT        NULL,
  PixFmt        TEXT        NULL,
  IsHdr         INTEGER NOT NULL DEFAULT 0,
  Rotation      INTEGER NOT NULL DEFAULT 0,
  TakenAt       TEXT        NULL,           -- EXIF 拍摄时间 ISO8601
  CameraModel   TEXT        NULL,
  ThumbPath     TEXT        NULL,           -- 相对 .cache/thumbs
  Status        TEXT    NOT NULL,           -- Pending|Processing|Ready|Failed|Missing
  ErrorMessage  TEXT        NULL,
  CreatedAt     TEXT    NOT NULL,
  UpdatedAt     TEXT    NOT NULL
);
CREATE UNIQUE INDEX UX_Assets_LibraryPath ON Assets(LibraryPath);
CREATE INDEX IX_Assets_FolderKey ON Assets(FolderKey);
CREATE INDEX IX_Assets_QuickHash ON Assets(QuickHash);
CREATE INDEX IX_Assets_Status    ON Assets(Status);

-- ============ 命名序号计数器 ============
CREATE TABLE NamingCounters (
  FolderKey TEXT PRIMARY KEY,               -- 运动会/开幕式
  NextIndex INTEGER NOT NULL                -- 下一个可用序号
);

-- ============ 后台任务 ============
CREATE TABLE Jobs (
  Id           INTEGER PRIMARY KEY AUTOINCREMENT,
  AssetId      INTEGER NOT NULL REFERENCES Assets(Id) ON DELETE CASCADE,
  JobType      TEXT    NOT NULL,            -- TranscodeVideo|ConvertPhoto|CopyAudio|Thumbnail
  Status       TEXT    NOT NULL,            -- Queued|Running|Paused|Done|Failed|Canceled
  Progress     REAL    NOT NULL DEFAULT 0,  -- 0.0 ~ 1.0
  Attempts     INTEGER NOT NULL DEFAULT 0,
  Priority     INTEGER NOT NULL DEFAULT 0,
  ErrorMessage TEXT        NULL,
  CreatedAt    TEXT    NOT NULL,
  StartedAt    TEXT        NULL,
  FinishedAt   TEXT        NULL
);
CREATE INDEX IX_Jobs_Status ON Jobs(Status, Priority DESC, Id);

-- ============ 配置 ============
CREATE TABLE Settings (Key TEXT PRIMARY KEY, Value TEXT NOT NULL);

-- ============ 统计视图 ============
CREATE VIEW v_LibraryStats AS
SELECT Kind, COUNT(*) AS Cnt, SUM(SizeBytes) AS TotalBytes
FROM Assets WHERE Status = 'Ready' GROUP BY Kind;
```

## 5. 核心流程

### 5.1 入库管线（最重要的一环）

**触发**：把文件/文件夹拖进主窗口。

```
【第 0 步 · 前置校验】(同步，毫秒级)
  ├─ 库根目录存在且有写权限
  ├─ 磁盘剩余空间 ≥ 待处理总大小 × 0.6  ← 预估 H.265 输出体积
  └─ 不足则弹出提示并中止（不做半途而废的导入）

【第 1 步 · 扫描入队】(异步，秒级，立刻给反馈)
  递归枚举拖入的路径
  ├─ 按扩展名分类 → Video / Photo / Audio
  ├─ 忽略：隐藏文件、.tmp、目录内的 .library.db 等
  └─ 对每个文件：
       ├─ QuickHash = XxHash64(文件大小 | 首 64KB | 尾 64KB)
       ├─ 查重（见 5.3）→ 命中则跳过并在 UI 提示"已存在 N 个，已跳过"
       ├─ 分配序号 ← 命名引擎（见 5.2）★ 此处即锁定最终文件名
       ├─ 写入 Assets 表，Status = Pending
       ├─ 写入 Jobs 表，Status = Queued
       └─ 从源文件抽 1 帧生成缩略图（转码与缩略图并行，互不阻塞）
  → 界面立刻出现卡片：带缩略图 + 文件名 + "排队中"角标

【第 2 步 · 后台 worker 处理】
  按 Kind 分发：

  ┌─ Video ─────────────────────────────────────────┐
  │ ffmpeg 直读 SourcePath                           │
  │   → 输出到 库根\.tmp\{guid}.mp4.tmp              │
  │   → 成功后 File.Move() 原子改名到目标路径        │
  │   → 源文件全程零改动                             │
  └──────────────────────────────────────────────────┘

  ┌─ Photo ─────────────────────────────────────────┐
  │ ffmpeg 读源（含 HEIC，走 mov demuxer）           │
  │   → 提取 EXIF（方向/拍摄时间/机型）写入 DB       │
  │   → AutoOrient() 应用方向  ★ 否则竖拍会躺倒       │
  │   → 编码 PNG → 写 .tmp → 原子改名                │
  └──────────────────────────────────────────────────┘

  ┌─ Audio ──────────────────────────────────────────┐
  │ 流式复制（不转码，几乎瞬间完成）                 │
  │   → 写 .tmp → 原子改名                           │
  └──────────────────────────────────────────────────┘

【第 3 步 · 收尾】
  更新 Status = Ready、SizeBytes、真实媒体信息
  ffprobe 回读库内文件校验完整性（时长/分辨率与预期一致）
  更新库空间统计
```

**关键设计点：**

| 设计 | 原因 |
|---|---|
| **原子落盘**（`.tmp` → `File.Move`） | 转码崩溃/断电，库里不会留半截垃圾文件 |
| **序号在第 1 步就锁定** | 占位卡片立刻显示最终文件名，不会转完再改名 |
| **`.tmp` 与库根同盘** | `File.Move` 才是原子的；跨盘会退化成复制+删除 |
| **缩略图与转码解耦** | 卡片秒出图，转码在后台慢慢跑，互不阻塞 |
| **直读源文件、库里只放成品** | 你的决策：省一半空间，且库里是实体 H.265 |
| **失败烧号不复用** | 序号出现空档（如 001,003）比序号冲突安全得多 |

**崩溃恢复**：启动时扫描 `.tmp` 目录 → 删除所有孤儿临时文件 → 把对应 Job 状态从 `Running` 回滚为 `Queued`（`Attempts + 1`）。

### 5.2 命名引擎

**规则**：`{最内层文件夹名}_{序号:D3}.{ext}`，序号在每个文件夹内独立。

```
D:\素材\运动会\开幕式\  拖入
  → FolderKey = "运动会/开幕式"       (由相对源路径推导)
  → 文件夹名   = "开幕式"
  → 库内路径   = 库根\运动会\开幕式\
  → 文件       = 开幕式_001.mp4, 开幕式_002.mp4, ...

单独拖一个文件 E:\随便\VID_1234.mp4
  → 最内层文件夹名 = "随便"（取该文件的父目录名）
  → 随便_001.mp4
```

**FolderKey 的推导**（拖入路径 → 库内相对目录）：

| 拖入 | FolderKey | 说明 |
|---|---|---|
| `D:\素材\运动会\开幕式\` | `运动会/开幕式` | 拖文件夹 → **用文件夹自身的名字作为一层** |
| `D:\素材\运动会\` | `运动会` | |
| `D:\素材\` 里的单个文件 | `<该文件的父目录名>` | 单文件时取父目录名 |
| 直接拖 `D:\` 根上的文件 | `未分类` | 兜底目录 |

> ⚠️ 拖文件夹时，**文件夹自身成为库内的一层目录**（`开幕式\` → 库内 `.../开幕式/`）。这是为了保留你的目录意图。

**序号分配**（事务内原子完成）：

```sql
BEGIN IMMEDIATE;
  INSERT INTO NamingCounters(FolderKey, NextIndex) VALUES (@k, 1)
    ON CONFLICT(FolderKey) DO NOTHING;
  UPDATE NamingCounters SET NextIndex = NextIndex + 1
    WHERE FolderKey = @k
    RETURNING NextIndex - 1 AS Allocated;
COMMIT;
```

**首次遇到新文件夹时**先播种计数器（防止库里已有文件导致从 001 重号）：

```sql
-- 扫描该目录下已存在的 文件夹名_NNN.* 取最大值 +1
SELECT MAX(CAST(SUBSTR(FileName, LENGTH(@prefix) + 1,
              INSTR(SUBSTR(FileName, LENGTH(@prefix) + 1), '.') - 1) AS INTEGER))
FROM Assets WHERE FolderKey = @k AND FileName LIKE @prefix || '_%';
```

**边界处理**：

| 情况 | 处理 |
|---|---|
| 序号 > 999 | 自动扩到 4 位（`_1000`），不与 3 位冲突 |
| 文件夹名含非法字符 `\ / : * ? " < > \|` | 替换为 `_` |
| 文件夹名以 `.` 或空格结尾 | 去除（Windows 不允许） |
| 文件夹名超长 | 截断到 60 字符 |
| 保留设备名（CON/PRN/AUX/NUL/COM1…） | 加前缀 `_` |
| 全中文/中文混排 | 直接支持（UTF-8 + NTFS） |

### 5.3 去重

**QuickHash 设计**：`XxHash64(文件大小 ‖ 首 64KB ‖ 尾 64KB)` → 16 位十六进制。

- 文件 < 128KB 时哈希整个文件
- 对几百个文件的规模，碰撞概率可忽略
- 比全文件 SHA-256 **快 50~100 倍**（几十 GB 素材用全哈希要几十分钟）

**判定**：`QuickHash` 相同 → 视为重复 → 跳过并在 UI 汇总提示。

> 未来可加"深度校验"选项（对哈希相同的文件再做全文件 SHA-256 确认），本期不做。

### 5.4 视频转码

#### 主命令（NVENC 硬件编码）

```
ffmpeg -hide_banner -nostdin -y
  -i "<源文件>"
  -map 0:v:0 -map 0:a?            # 首条视频轨 + 全部音轨（无音轨也不报错）
  -c:v hevc_nvenc
  -preset p5 -tune hq             # p1(最快)~p7(最慢)，p5 为画质/速度平衡点
  -rc vbr -cq 24 -b:v 0           # 恒定质量模式，cq 24 ≈ 视觉无损
  -profile:v main -pix_fmt yuv420p
  -tag:v hvc1                     # ★ 关键：无此标记部分软件播不了 HEVC-MP4
  -c:a copy                       # 音频已兼容时直接复制，零损失零耗时
  -movflags +faststart            # moov 前置，拖动进度条响应更快
  -progress pipe:1 -nostats       # 机器可读进度
  "<库根>\.tmp\<guid>.mp4.tmp"
```

#### 音频编解码策略

先 `ffprobe` 探测音轨，再决定：

| 源音频编码 | 参数 | 原因 |
|---|---|---|
| `aac` / `mp3` / `ac3` | `-c:a copy` | MP4 容器兼容，直接复制（最快） |
| `pcm_*` / `flac` / 其他 | `-c:a aac -b:a 192k` | MP4 装不下，必须转 |
| 无音轨 | `-map 0:a?` 自动忽略 | |

#### 兜底命令（NVENC 不可用时）

```
-c:v libx265 -crf 24 -preset medium -x265-params log-level=error
```
速度约为 NVENC 的 1/10，但保证任何机器都能跑。

#### NVENC 可用性探测（启动时执行一次并缓存）

```
ffmpeg -hide_banner -f lavfi -i nullsrc=s=256x144:d=1 -c:v hevc_nvenc -f null -
```
返回码 0 → 可用；否则回退 `libx265`。

> ⚠️ **阶段0 实测踩到的坑**：你的 RTX 5060 Laptop（Blackwell）**不是**"ffmpeg 版本够新就行"——
> 新 ffmpeg 反而要求更新的 **显卡驱动**：
>
> | ffmpeg | NVENC 要求 | 你的驱动 596.36 |
> |---|---|---|
> | **8.1.3** | NVENC API 13.0 | ✅ **可用** |
> | 9.0.2 | NVENC API 13.1（驱动 ≥610.00） | ❌ `Required: 13.1 Found: 13.0` |
>
> **所以打包 8.1.3，不是 9.0.2。**
> 若将来自动更新 ffmpeg，**必须重新跑一次 NVENC 探测**，否则会静默退化成 CPU 编码（慢 10 倍）。
>
> GeForce 驱动对并发 NVENC 会话有限制，因此**转码 worker 并发数设为 2**。

#### ⚠️ HDR / 10-bit 源的处理

iPhone 等设备录制的 HDR 视频是 10-bit（HLG/PQ）。强行压成 8-bit `yuv420p` 会导致**色彩严重失真**（发灰、过曝）。

**本方案默认**：检测到源为 10-bit 或 HDR →

```
  -profile:v main10 -pix_fmt p010le   # 保留 10-bit
  # 同时原样传递色彩元数据（ffmpeg 默认透传 color_primaries/trc/matrix）
```
并在 UI 提供"强制转 SDR（色调映射）"开关供特殊需求使用。

### 5.5 照片处理（ffmpeg）

```
读取源文件（HEIC / JPEG / PNG / TIFF / WebP / BMP）

  ① 先读 EXIF（MetadataExtractor，纯托管，不碰像素）
       Orientation / DateTimeOriginal / Make / Model / GPS
         → 写入 Assets.TakenAt / CameraModel / Rotation

  ② 再转 PNG（ffmpeg）
       ffmpeg -hide_banner -y -i "<源>"
              -map 0:v:0                      # ★ 必须显式指定
              -frames:v 1 -update 1
              -pix_fmt rgb24                  # 8-bit PNG
              -pred mixed -compression_level 6
              "<库根>\.tmp\<guid>.png.tmp"

  → 原子改名落盘
```

**三个参数的由来（都有实测支撑）：**

| 参数 | 为什么 |
|---|---|
| `-map 0:v:0` | HEIC 是**多图容器**。样张 `sample1.heic` 内含 2 个流（1440x960 主图 + 240x160 缩略图）。显式取第一路主图，避免行为不确定 |
| `-pix_fmt rgb24` | 输出 8-bit PNG。10-bit HDR 照片会在此降为 8-bit（体积换兼容性，符合你的使用场景） |
| `-pred mixed -compression_level 6` | **实测最优组合**，见下表 |

**EXIF 方向由 ffmpeg 自动应用**（实测 1600x900 → 900x1600），无需手写 `transpose` 滤镜。
> 若要手动控制，`transpose=1` 是"顺时针 90°"，但它**不会**读 EXIF，是把画面硬转，用错会双重旋转。

#### PNG 编码参数实测（4000x3000 照片，源 JPEG 21.79 MB）

| 编码器 / 参数 | 输出体积 | 耗时 |
|---|---|---|
| Magick.NET level=6（初版方案） | 29.76 MB | 3.80 s |
| **ffmpeg `-pred mixed -compression_level 6`** | **30.76 MB** | **2.20 s** |
| ffmpeg `-pred none -compression_level 6` | 30.76 MB | 2.24 s |
| ffmpeg `-pred paeth -compression_level 6` | 33.79 MB | 1.52 s |
| ffmpeg `-pred avg -compression_level 6` | 34.45 MB | 1.30 s |
| ffmpeg `-pred sub/up` | 33.88 MB | 1.50 s |

**结论：`-pred mixed` 比默认的 `paeth` 小 9%、只慢 0.7 秒；
相比 Magick.NET 仅大 3.4%，却快 1.7 倍。**

> ⚠️ `compression_level` 6 与 9 输出体积完全相同（FFmpeg 的 zlib 上限），**用 6 即可，9 纯属浪费**。

#### 并发与吞吐

→ **照片 worker 并发数设为 4**（i7-14650HX 有 24 线程，绰绰有余）。
300 张 24MP 照片按 2.2 秒/张、4 并发计算 ≈ **3 分钟**完成。

**体积预警**：程序会实时统计库占用，剩余空间低于阈值（默认 10 GB）时在任务条显示红色警告，并提供"后续照片改存 JPG"的一键开关。

### 5.6 音频处理

**仅复制，不转码**（你的决策）。流式复制 + 原子落盘，几十 MB 的文件瞬间完成。

**缩略图**：优先生成**波形图**（比专辑封面对剪辑更有用）：

```
ffmpeg -i "<源>" -filter_complex "showwavespic=s=320x180:colors=0x4A9EFF" \
       -frames:v 1 "<thumb>.png"
```

### 5.7 缩略图服务

| 类型 | 生成方式 |
|---|---|
| 视频 | `ffmpeg -ss <时段> -i "<源>" -frames:v 1 -vf scale=320:-2 -q:v 3` |
| 照片 | ffmpeg 缩放 → JPEG q80 |
| 音频 | 波形图（失败则回退为通用音频图标） |

**抽帧时段选择**：`min(时长 × 10%, 10 秒)`。
→ 避开片头的黑场/场记板，比固定抽第 1 帧有意义得多。

> `-ss` 放在 `-i` **之前** = 快速定位（关键帧级），速度提升几十倍。

**缓存**：`E:\MediaLibrary\.cache\thumbs\{QuickHash}.jpg`，320px 宽。
- 按 hash 命名 → 同一素材重复出现时**零成本复用**
- 缓存丢失可随时重建，不是关键数据
- 磁盘上限 2 GB，LRU 清理

**内存优化（滚动流畅的关键）**：

```csharp
// ★ 必须用 OnLoad，否则 BitmapImage 会一直占用文件句柄，
//   导致缩略图文件无法删除/重建
var bmp = new BitmapImage();
bmp.BeginInit();
bmp.CacheOption  = BitmapCacheOption.OnLoad;
bmp.DecodePixelWidth = 320;   // 按需解码，几十 MB 原图也不会吃内存
bmp.UriSource = new Uri(thumbPath);
bmp.EndInit();
bmp.Freeze();                 // 冻结后可跨线程共享
```
外加 LRU 缓存（上限 500 张已解码位图，约 100~150 MB）。

### 5.8 悬浮预览（体验核心）

#### 架构

```
LibVLC (单例，App 启动时创建，约 100ms 开销 → 只付一次)
  ├─ MediaPlayer #hover   ← 悬浮预览专用，全程复用不销毁
  └─ MediaPlayer #full    ← 空格键放大预览用
```

**预热策略**：`LibVLC` 实例在 App 启动时后台创建，避免第一次悬停时卡 300ms。

#### 交互时序

```
鼠标进入卡片
   │
   ├─ 立刻显示【已缓存的缩略图】        ← 0ms，绝对无闪烁
   │
   ├─ 启动 280ms 防抖计时器
   │     └─ 期间鼠标移出 / 移到别的卡片 → 取消，什么都不做
   │
   ▼ 计时器到期
定位悬浮窗口（跟随鼠标，钳制在鼠标所在显示器的 WorkArea 内，支持多显示器 DPI）
调用 mediaPlayer.Play(new Media(path))
   │
   ├─ 视频：Volume = 0（静音），显示画面 + 可拖动进度条
   └─ 音频：Volume = 80，显示波形图 + 可拖动进度条
   
鼠标移出卡片
   ├─ 进入"宽限期" 400ms（允许你移进悬浮窗去拖进度条）
   ├─ 宽限期内移回 → 取消隐藏，继续播放
   └─ 超时 → mediaPlayer.Stop() + window.Hide()
```

#### 两个必须解决的问题

**问题 1：不能同时播放多个。**
全局只有一个 `MediaPlayer #hover`，物理上不可能同时播放。切换卡片时先 `Stop()` 再 `Play()`。

**问题 2：WPF + LibVLC 的"空域问题"（Airspace）—— ✅ 阶段0 已实测确认**

> 初版此处写的是"硬限制（推测）"。阶段0 用**带对照组**的方法做了严格验证，结论确凿。
> 完整证据见 `阶段0验证报告.md` §3。

**验证方法**：在视频区域正中放一个亮红方块，然后
① 无视频时截图（对照组，应为红色）→ ② 播放中截图（探针是否消失）→ ③ 收起探针看像素是否变化。

**实测数据**：

| 步骤 | 探针区域平均 RGB | 判定 |
|---|---|---|
| 对照组（无视频） | **(189, 66, 0)** | 红色 ✅ 测量方法有效 |
| 实验组（播放中） | **(128, 118, 140)** | 视频内容，红色**不可见** ❌ |
| 二次信号 | 收起探针 → **0.0%** 像素变化 | 探针从未影响屏幕 ❌ |

**结论：`LibVLCSharp.WPF.VideoView` 确实盖住了一切 WPF 元素。**

| 能力 | 是否可行 |
|---|---|
| WPF 元素覆盖在视频画面上 | ❌ **确认不可能** |
| 视频区域圆角 / 半透明 / 阴影 | ❌ **确认不可能** |
| 用 `Popup` 承载 | ❌ 会与原生窗口抢层级，闪烁 |
| 用 `AllowsTransparency=true` 的窗口 | ❌ 分层窗口与子 HWND 不兼容 |
| **独立无边框 `Window`** | ✅ **唯一可靠方案（实测 Show 16ms / Hide 2ms）** |

**悬浮窗口配置**：

```xml
<Window WindowStyle="None" ResizeMode="NoResize"
        ShowInTaskbar="False" ShowActivated="False"
        Topmost="True" AllowsTransparency="False" Background="#1E1E1E">
```
- `AllowsTransparency="False"` → 视频区域必须是不透明直角矩形
- **窗口只创建一次**，之后反复 `Show()`/`Hide()`（实测 16ms / 2ms；重建窗口反而有明显闪烁）
- 视觉妥协：视频区直角；进度条/文件名条可以正常设计，但整体窗口为矩形

#### ⚠️ `ShowActivated="False"` 不足以防止抢焦点

阶段0 实测：即使设了 `ShowActivated="False"`，日志里仍出现
`HoverWindow.OnActivated 被触发` → **悬停时会抢走你的输入焦点**（打字被打断，很难忍）。

**必须额外设置扩展窗口样式：**

```csharp
const int GWL_EXSTYLE      = -20;
const int WS_EX_NOACTIVATE = 0x08000000;   // 显示/点击都不激活
const int WS_EX_TOOLWINDOW = 0x00000080;   // 不出现在 Alt+Tab

var hwnd  = new WindowInteropHelper(hoverWindow).Handle;
var style = GetWindowLong(hwnd, GWL_EXSTYLE);
SetWindowLong(hwnd, GWL_EXSTYLE, style | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW);
```
**必须在阶段 3 实测确认生效**（已列入验收项）。

#### ⚠️ 悬浮窗定位必须处理 DPI 缩放

阶段0 在 **200% DPI** 环境下踩到了这个坑（你的屏幕也是 200%）：

`UIElement.PointToScreen()` 返回**物理像素**，而 `ActualWidth/Height` 是 **DIP**。
混用会导致窗口定位算错。**必须用两个角点分别转换：**

```csharp
var tl = el.PointToScreen(new Point(0, 0));
var br = el.PointToScreen(new Point(el.ActualWidth, el.ActualHeight));   // DIP 值传给 PointToScreen 是对的
var rect = Rectangle.FromLTRB(tl.X, tl.Y, br.X, br.Y);                    // 得到物理像素矩形
```

错例（会导致高 DPI 下缩略图卡片定位偏移）：
```csharp
// ❌ 两个坐标系混用
new Rectangle(tl.X, tl.Y, (int)el.ActualWidth, (int)el.ActualHeight);
```

### 7.1 线程模型

| 角色 | 数量 | 说明 |
|---|---|---|
| UI 线程 | 1 | WPF Dispatcher |

| 数据库读取 | 池化 | WAL 模式允许并发读 |

### 7.2 任务队列

```csharp
// 有界 Channel 做背压，防止拖入一万个文件时内存爆掉
var channel = Channel.CreateBounded<JobMessage>(
    new BoundedChannelOptions(256) { FullMode = BoundedChannelFullMode.Wait });
```
- 启动时从 `Jobs` 表加载 `Queued` 任务重新入队（**断电重启自动续跑**）

## 8. 错误处理与边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | 转码中途源文件被移走/删除 | Job → `Failed`，提示"源文件已不可用"，卡片可右键**重新定位源文件** |
| 2 | 磁盘空间不足 | 导入前预检；转码中实时检查，不足则**暂停队列**并红色告警 |
| 3 | 应用崩溃 / 断电 | 启动清 `.tmp` 孤儿 + `Running` 任务回滚为 `Queued`（`Attempts+1`） |
| 4 | 失败重试超 3 次 | 标记 `Failed` 不再自动重试，避免死循环 |
| 5 | 文件名非法字符 / 超长 | 替换非法字符 + 截断；启用 `longPathAware` 支持 >260 字符路径 |
| 6 | 同名文件夹合并 | **已知副作用**，见 §1.2 R9 附录说明 |
| 7 | 序号超 999 | 自动扩到 4 位 |
| 8 | 库文件被外部删除 | 启动巡检 → `Missing` → 卡片置灰，可右键"移除记录" |
| 9 | 竖拍照片躺倒 | `AutoOrient()` 处理（第 5.5 节） |
| 10 | 竖拍视频（rotation 元数据） | ffmpeg 默认 `-autorotate` 自动烘焙旋转 |
| 11 | 无音轨视频 | `-map 0:a?` 可选映射，不报错 |
| 12 | 多音轨视频 | 全部保留 |
| 13 | HDR / 10-bit 源 | 保留 `main10` + 色彩元数据，不做有损压平（§5.4） |
| 14 | NVENC 不可用 | 自动回退 `libx265`，UI 提示速度会变慢 |
| 15 | 损坏的媒体文件 | `ffprobe` 探测失败 → `Failed`，提示"文件可能已损坏" |
| 16 | 拖入库自身目录 | 检测并拒绝，防止无限递归 |
| 17 | 拖入的文件夹名与库内已有不同源文件夹同名 | 合并 + 序号连续（已确认接受） |
| 18 | 移动硬盘中途拔出 | IO 异常 → 失败并给出清晰提示 |
| 19 | 库根目录被删/不可写 | 启动检测，提示重新选择库位置 |
| 20 | Schema 版本高于程序 | 拒绝打开，提示升级程序 |

**实现要点：**

| 关注点 | 方案 |
|---|---|
| 暂停语义 | 暂停=排队任务标记 `Paused`；**执行器在开始新任务前在暂停门等待**，运行中的优雅跑完（不打断 ffmpeg 半截输出）。`MarkRunning` 仅对 `Queued` 生效，等待期间被取消/暂停的任务自动跳过 |
| 单任务取消 | `JobQueueService` 维护运行中任务的 CancellationTokenSource 注册表：先改库（→ Canceled）再打断 worker；处理器清理 `.tmp` 并把素材退回 `Pending`，与"应用关闭"的取消区分开 |
| 崩溃恢复 | 启动时 `Running → Queued`（原有机制保留），配合暂停门形成完整状态机：`Queued ⇄ Paused`、`Running → Done/Failed/Canceled` |
| 入队路由 | 导入与重新转码统一走 `JobQueueService.EnqueueManyAsync`，**暂停状态下新任务直接进 Paused**，不会绕过暂停 |
| 批量重命名 | 模板占位符 + 连续序号；目标撞名自动 `_2` 后缀；文件与 DB 记录同步更名 |
| 回收站 | `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(..., SendToRecycleBin)`，文件可还原 |
