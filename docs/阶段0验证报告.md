## 2. 【发现 1】NVENC：必须打包 ffmpeg 8.1.3 而非 9.0.2

### 实测错误

```
[hevc_nvenc] Driver does not support the required nvenc API version.
             Required: 13.1  Found: 13.0
             The minimum required Nvidia driver for nvenc is 610.00 or newer
```

- 你的驱动：**596.36**（2026-04-23）
- ffmpeg 9.0.2 要求：**≥ 610.00**

### 版本对照实测

| ffmpeg | 版本串 | NVENC 结果 |
|---|---|---|
| 9.0.2 | `n9.0.2-8-gb135b25c19-20260925` | ❌ 失败（exit -40） |
| 8.1.3 | `n8.1.3-20260925` | ✅ **成功**，输出 2137 KB |

### 决策：打包 ffmpeg 8.1.3

**理由**：开箱即用，用户无需做任何事。8.1 已支持我们需要的全部功能（`hevc_nvenc`、`libx265`、HDR/10-bit、HEIC 读取）。

**另一个选项**：你手动把 NVIDIA 驱动升到 610.00+，然后就能用 9.0.2。但没必要——9.x 相对 8.x 的新东西（VVC、动态 WebP）跟素材管理无关。

> 程序里仍保留 **NVENC 探测 + `libx265` 自动回退**（见设计文档 §5.4）。
> 顺带实测了 CPU 兜底性能：1080p 2 秒视频用 `libx265 -preset medium` 编码耗时 1.3 秒（约 1.5 倍实时）。

## 3. 【发现 2】空域问题——严格确认

这是本次验证做得最严谨的一项。**关键是有对照组**，避免"测了个寂寞"。

### 方法

在视频区域正中央放一个 **亮红色方块**（`#FFFF0000` + 绿边），然后：

1. **对照组**：视频未加载时，截取探针区域 → 应该看到红色（证明测量方法有效）
2. **实验组**：视频播放中，截取同一区域 → 如果红色消失，说明视频盖住了它
3. **二次信号**：暂停视频，把探针 `Collapsed`，看屏幕像素是否变化

### 实测数据

| 步骤 | 探针区域平均 RGB | 判定 |
|---|---|---|
| 对照组（无视频） | **(189, 66, 0)** | 红色 ✅ 测量方法有效 |
| 实验组（播放中） | **(128, 118, 140)** | 视频内容，红色**已不可见** ❌ |
| 二次信号 | 收起探针 → **0.0%** 像素变化 | 探针从未影响屏幕 ❌ |

### 结论

**空域问题确凿成立。** `LibVLCSharp.WPF.VideoView` 底层是原生子窗口，WPF 元素**无法**绘制在其之上。

**这直接锁定了设计文档 §5.8 的约束，且不可协商：**

- ❌ 视频区域**不能**有圆角、阴影、半透明
- ❌ **不能**用 `Popup` 承载预览
- ❌ **不能**用 `AllowsTransparency=true`
- ✅ **唯一可行**：独立无边框 `Window` + 不透明矩形

> 好消息：独立窗口的表现很好——Show 16ms、Hide 2ms，对悬浮预览完全够用。

## 4. 【发现 3】悬浮窗会抢焦点

### 实测

即使设置了 `ShowActivated="False"`，日志里仍出现：

```
[12:20:31.855] HoverWindow.OnActivated 被触发（注意：若出现说明抢焦点了）
```

### 影响

你正在编辑器里打字，鼠标划过素材库 → **焦点被抢走**。这是个很难忍的体验问题。

### 缓解方案（已写入设计文档）

在悬浮窗 HWND 上设置扩展样式：

```csharp
const int GWL_EXSTYLE      = -20;
const int WS_EX_NOACTIVATE = 0x08000000;   // 点击/显示都不激活
const int WS_EX_TOOLWINDOW = 0x00000080;   // 不出现在 Alt+Tab

var hwnd = new WindowInteropHelper(hoverWindow).Handle;
var style = GetWindowLong(hwnd, GWL_EXSTYLE);
SetWindowLong(hwnd, GWL_EXSTYLE, style | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW);
```

**必须实测确认**（阶段 3 的验收项之一）。

## 5. 【发现 2 的延伸】ffmpeg 能读 HEIC —— 我最初的判断是错的

### 我一开始错在哪

我 grep 了 ffmpeg 的 demuxer 列表找 `heif`，没找到，就下了"ffmpeg 读不了 HEIC"的结论。

**这是假阴性。** 实际原因是：**HEIF 与 MP4 同为 ISOBMFF 容器**，ffmpeg 直接用 `mov,mp4,m4a,3gp,3g2,mj2` demuxer 就解开了。

### 实测证据

```
$ ffprobe sample1.heic
codec_name=hevc   width=1440  height=960  nb_frames=1
format_name=mov,mp4,m4a,3gp,3g2,mj2
format_long_name=QuickTime / MOV

$ ffmpeg -i sample1.heic -frames:v 1 out.png
>>> 成功，输出 2536 KB，1440x960
```

### 两个工具的能力对照

| 能力 | ffmpeg 9.0.2 | Magick.NET 14.17.1 |
|---|---|---|
| 读 HEIC | ✅ | ✅ `Heic(R-)` |
| 读 HEIC 网格分块（>512px） | ✅ (1440x960) | ✅ |
| 写 HEIC | ❌ | ❌ `(R-)` 只读 |
| 自动应用 EXIF 方向 | ✅ **900x1600** | ✅ **900x1600** |
| HEIC → PNG | ✅ 2536 KB / 1440x960 | ✅ 2711 KB / 1440x960 |
| 解码耗时 | — | 129 ms |
| 体积代价 | 已在包里 | **额外 24 MB 原生库** |

### 决策建议：**移除 Magick.NET，统一用 ffmpeg**

- ffmpeg 已经必须打包（视频转码），照片复用它 → **少一个工具链、少 24 MB、少一类失败模式**
- EXIF 元数据（拍摄时间/机型）改用 **MetadataExtractor** 读取（纯托管库，约 1 MB，实测能读 HEIC 的 6 个目录）
- 设计文档里的 `IImageConverter` 抽象保留 → 万一遇到 ffmpeg 读不了的图片格式，**可以随时把 Magick.NET 加回来**

> 我原本基于"ffmpeg 无 libheif"把 Magick.NET 列为"必需"。这个结论作废，但验证过程本身是有价值的——
> 至少现在我们知道两条路都通，且 AutoOrient 有确凿证据。

### 竖拍转向的确定性验证

因为 Magick.NET 用 API 写 `Orientation` 标签不生效，我改用**字节级注入 EXIF APP1 段**，构造了一张确定带 `Orientation=6` 的 JPEG：

```
MetadataExtractor: Orientation=Right side, top (Rotate 90 CW)
Magick.NET    读到 Orientation=6
AutoOrient:    1600x900 -> 900x1600   PASS 竖拍已正确转正
ffmpeg:        输出 900x1600          PASS
```

**两条路都正确。** 设计文档 §5.5 的竖拍处理有据可依。

### ⚠️ 新增注意：HEIC 是多图容器

`sample1.heic` 内含 **2 个流**（1440x960 主图 + 240x160 缩略图）。

- ffmpeg 默认取第一个流 → 正确
- 但**必须显式 `-map 0:v:0`**，否则行为不确定

## 6. 【打包发现】libvlc 默认会塞进三个架构，共 299 MB

### 问题

`VideoLAN.LibVLC.Windows` 的 targets 文件逻辑：

```xml
<VlcWindowsX64Enabled    Condition="... '$(Platform)'=='x64' OR '$(Platform)'=='AnyCPU'">true</...>
<VlcWindowsX86Enabled    Condition="... '$(Platform)'=='x86' OR '$(Platform)'=='AnyCPU'">true</...>
<VlcWindowsArm64Enabled  Condition="... '$(Platform)'=='ARM64' OR '$(Platform)'=='AnyCPU'">true</...>
```

**`Platform=AnyCPU` 时三套全部启用**（这是 .NET 项目的默认值）。

### 实测

| 架构 | 大小 | 文件数 |
|---|---|---|
| win-x64 | 106.4 MB | 422 |
| win-x86 | 103.1 MB | 422 |
| win-arm64 | 89.7 MB | 409 |
| **合计** | **299.3 MB** | |
| 总输出目录 | **325.3 MB** | |

### 修复（已验证）

在 csproj 里显式关闭多余架构：

```xml
<VlcWindowsX64Enabled>true</VlcWindowsX64Enabled>
<VlcWindowsX86Enabled>false</VlcWindowsX86Enabled>
<VlcWindowsArm64Enabled>false</VlcWindowsArm64Enabled>
```

**结果：输出 325.3 MB → 132.5 MB，省下 193 MB。**

## 7. 其他实测数据（用于校准设计文档）

### 7.1 PNG 编码性能（4000x3000 照片）

| compression-level | 输出体积 | 耗时 |
|---|---|---|
| 3 | 31.19 MB | 3.35 s |
| **6** | **29.76 MB** | **3.80 s** |
| 9 | 29.76 MB | 3.60 s |

**结论：level 6 是甜点**（6 和 9 体积相同，但 6 更快）。设计文档 §5.5 的选择得到验证。

> 注意：测试用的合成图带高斯噪声，压缩率偏低（膨胀仅 1.37x）。
> 真实照片（细节少、平坦区域多）膨胀会更明显，**3~6 倍是合理预期**，设计文档 §1.2 的体积预警保持不变。

### 7.2 VLC 播放性能

| 指标 | 实测 |
|---|---|
| `Play()` 到 `Playing` 状态 | **43 ~ 56 ms** |
| Seek 精度 | 设 0.500 → 实际 0.565（关键帧对齐，符合预期） |
| 悬浮窗 `Show()` | 16 ms |
| 悬浮窗 `Hide()` | 2 ms |
| 非边框窗口 + VideoView 构造 | 正常 |

**结论：悬浮预览的 280ms 防抖 + 400ms 宽限期参数合理，实际响应会很快。**

### 7.3 CPU 兜底编码性能

1080p / 2 秒 / `libx265 -preset medium -crf 24` → **1.3 秒**（约 1.5 倍实时）
推算：10 分钟 1080p 约 6~7 分钟。可接受，但 NVENC 会快得多。

### 7.4 环境参数

| 项 | 值 |
|---|---|
| 屏幕 | 1280x800，**DPI 缩放 200%** |
| .NET SDK | 10.0.203 / 运行时 10.0.7 |
| libvlc | 3.0.24 Vetinari |
| ffmpeg | 8.1.3（推荐打包）/ 9.0.2（NVENC 不可用） |

> ⚠️ **DPI 200% 带来一个实现陷阱**（已实测踩到）：
> `UIElement.PointToScreen()` 返回**物理像素**，而 `ActualWidth/Height` 是 **DIP**。
> 混用会导致坐标算错。必须用两个角点分别转换：
> ```csharp
> var tl = el.PointToScreen(new Point(0, 0));
> var br = el.PointToScreen(new Point(el.ActualWidth, el.ActualHeight));
> var rect = Rectangle.FromLTRB(tl.X, tl.Y, br.X, br.Y);
> ```
> 这直接影响**悬浮预览窗口的定位**，阶段 3 必须按此实现。
