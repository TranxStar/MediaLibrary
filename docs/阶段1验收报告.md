## 3. 过程中发现并修复的 3 个真实缺陷

### 缺陷 1（严重）：枚举被存成整数，导致所有按状态过滤的查询静默失效

**发现方式**：冒烟测试的"缩略图全部生成成功"检查显示「成功 0 / 失败 0」——一个都没跑。

**根因**：`DapperSetup` 里注册的枚举类型处理器**不生效**。把整个实体对象当 Dapper 参数时，
Dapper 退回默认行为，把枚举按底层整数写入库：

```
[诊断] Status 列实际存储值: '2'×200          ← Ready 的枚举值，不是 'Ready'
[诊断] Kind   列实际存储值: '0'×40 | '1'×150 | '2'×10
```

因为 `Status` 存的是 `'2'`，所有 `WHERE Status = 'Ready'` 的查询都匹配不到任何行 →
补全队列永远是空的 → 缩略图一张都不会生成。**这个 bug 会让整个软件在"看起来正常"的情况下完全丧失核心功能。**

**修复**：写库时一律显式 `enum.ToString()`（见 `AssetRepository.BuildParams`），
不依赖 Dapper 的内部行为；读取方向仍用类型处理器。

**修复后**：`'Ready'×200`、`'Video'×40 | 'Photo'×150 | 'Audio'×10`，补全队列 200 项全部处理成功。

> 📌 **这条已写入代码注释**（`DapperSetup` 与 `AssetRepository.BuildParams`），
> 避免以后有人"顺手清理"掉显式转换而重新引入。

### 缺陷 2：补全循环的轮数上限算错，永远处理不完

**根因**：`EnrichAllAsync` 用 `MaxAttempts`(3) 当循环轮数上限，而每轮批量是 48：

```
最多处理 4 轮 × 48 = 192 项，剩下 8 项永远不处理
```

200 个素材时表现是「补全 192 项，剩余 8 项」；素材更多时缺口更大。

**修复**：轮数上限改为按待办总量推导 —— `(pending / BatchSize) + MaxAttempts + 2`。
多出的轮数用于消化"整批都失败"的情况（失败会累加尝试计数，最终自然淘汰，不会死循环）。

### 缺陷 3（测试侧）：PowerShell 变量后跟冒号被当成作用域限定符

生成测试素材时，`"sine=frequency=$freq:duration=$dur"` 里的 `$freq:` 被 PowerShell
解析为作用域限定变量名（`$scope:name` 语法），传给 ffmpeg 的实际是 `frequency=:duration=2`：

```
Unable to parse "frequency" option value "=2"
```

40 个视频全部生成失败，而且因为 `-loglevel error | Out-Null` 把错误吞掉了，第一轮完全没发现。

**修复**：改用 `${freq}` 显式界定变量边界。已修正并重新生成 40 个视频。

> 教训：测试素材生成必须校验**产物数量**，不能只信任脚本的计数。

### 一个重要副产物：内容哈希去重生效

200 个素材只有 **79 种唯一内容** —— 测试素材里 121 个文件内容重复（合成图序列的相同帧）。
缩略图按内容哈希命名，因此只生成 79 个文件，重复内容**零成本复用**。

这验证了设计文档 §5.7 的缓存策略在真实场景下确实省空间。
