## 0. 交付后修复（2026-09-26 追加）

### 修复 A：预览挡住下方卡片 + "固定位置窗口中间"

用户反馈："挡住了下面的卡片，划不过去"、"预览窗位置不对，希望悬停在 a 图片就在 a 图片附近出现"。

**根因**：预览窗 840×560 物理像素，卡片只有约 140 逻辑高，它必然盖住下方两整行卡片。
而它又必须接收鼠标（拖进度条），被盖住的卡片根本碰不到。

**修法：跟随定位**（等价于画面区可穿透）+ 就近四选一定位（右侧优先 → 左侧 → 下方 → 上方）。

另有隐性根因：**空格固定预览**会把窗口钉在屏幕正中且忽略一切悬停，而界面上毫无提示。
修复：固定后悬停其他卡片自动取消固定；加"📌 已固定"角标；空格仅在网格有焦点时生效。

### 修复 B：光标置于"悬浮窗与卡片重合处"时预览闪烁（一会出现一会消失）

用户实测反馈。这是<b>最凶险的一类 bug</b> —— 由窗口架构的固有特性引发：

**根因**：预览窗的视频画面是**原生子窗口**（空域问题的另一面），它会**吞掉所有 WPF 鼠标事件**。
于是"鼠标移进预览窗 → 取消隐藏倒计时"这条信号永远发不出来：

```
鼠标从卡片 A 移到预览窗画面上
  ├─ 卡片 A 的 MouseLeave → 启动"400ms 后隐藏"倒计时 ✓
  ├─ 预览窗的 MouseEnter 永远不触发（事件被原生视频窗吞了）→ 倒计时没人取消 ✗
  └─ 400ms 后预览被定时杀掉
       → 鼠标落在被盖住的卡片 B 上 → MouseEnter → 280ms 后预览又弹出
       → 再被杀 → 再弹出…… 循环 = 用户看到的闪烁
```

**修法：光标轮询彻底取代窗口鼠标事件**（60ms 定时器，只问系统"光标现在在哪"）：

1. 光标在预览窗上 → **无条件取消隐藏倒计时**（预览绝不能死在用户眼下）
   - 画面区 → 跟随到鼠标下方那张卡片
   - 控制栏 → 不跟随，留给拖进度条
2. 光标不在预览窗、不在任何卡片（空白/树/工具栏）→ 启动隐藏倒计时（只启动一次，防重置）
3. 光标在卡片上 → 停倒计时，交给卡片的 MouseEnter/MouseLeave 管理

**验证**（新增 3 项诊断，共 21/21 通过）：

```
HOVER PASS | 光标压在预览窗上 1 秒，预览始终可见（不闪烁）
HOVER PASS | 压在重合位置时预览跟到了下方的卡片
HOVER PASS | 光标移到非卡片区域后预览会隐藏
```

> 教训：**不要信任被 HwndHost 盖住的区域的任何 WPF 鼠标事件**。
> 阶段0 只验证了"WPF 元素盖不住视频"，这次补上了它的另一面："视频也吞掉 WPF 的鼠标事件"。
> 凡是涉及原生子窗口区域的交互判断，一律用轮询系统光标兜底。

> 设计文档 §9 阶段 3 要求：悬停 ≤400ms 出画面；拖进度条流畅；

## 2. 实现要点

### 2.1 架构

```
AssetTile (MouseEnter/Leave)
   └─ 冒泡路由事件 HoverStarted / HoverEnded
        └─ MainWindow 处理器
             └─ HoverPreviewController（单例）
                  ├─ 防抖 280ms / 宽限 400ms
                  ├─ 物理像素定位 + 工作区钳制
                  └─ HoverPreviewWindow（单例，只创建一次）
                       └─ VlcPlayerPool.HoverPlayer（全局唯一播放器）
```

**"不会同时播多个"是结构性保证**：全局只有一个 `MediaPlayer`，
物理上不可能同时播放两路。

### 2.2 阶段0 结论的落地

| 阶段0 发现 | 阶段3 的处理 |
|---|---|
| 空域问题确凿存在 | 悬浮窗用独立无边框窗口；视频区直角；**音频模式不挂 VideoView**（否则原生子窗口会盖住波形图） |
| `ShowActivated=False` 挡不住抢焦点 | 追加 `WS_EX_NOACTIVATE` + `WS_EX_TOOLWINDOW` 窗口样式 |
| DPI 200% 下坐标单位混用会算错 | 用 `SetWindowPos` 传**物理像素**，绕开 WPF 的 DIP 换算 |
| 窗口反复 Show/Hide 比重建快 | 窗口只创建一次，加**启动时预热**（见 §3.1） |

### 2.3 交互时序

```
鼠标进入卡片
  ├─ 立即显示已缓存的封面（0ms，无闪烁）
  ├─ 启动 280ms 防抖
  │    ├─ 期间移出/移到别的卡片 → 取消，什么都不做
  │    └─ 到期 → 定位 + 播放
  └─ 视频静音 / 音频音量 80 / 照片只显示放大图

鼠标移出卡片 → 400ms 宽限期
  ├─ 期间移回，或移进悬浮窗本体 → 取消隐藏（可以拖进度条）
  └─ 超时 → Stop + Hide

滚动 / 移动窗口 / 最小化 / Esc → 立即隐藏
空格键 → 固定放大预览（居中显示，不自动隐藏）
```

### 2.4 进度条拖动

拖动期间置位 `_isScrubbing`，阻止 100ms 的定时器回写滑块：

```csharp
Position.PreviewMouseLeftButtonDown → _isScrubbing = true;
Position.PreviewMouseLeftButtonUp   → _player.Position = (float)Position.Value; _isScrubbing = false;
// 定时器：if (_isScrubbing) return;  // 不回写，否则会和用户的手抢滑块
```

同时覆盖"拖 thumb"和"点轨道"两种操作（`IsMoveToPointEnabled=True`）。

## 3. 过程中发现并修复的 4 个问题

### 问题 1（严重）：首次悬停要 1.7 秒

**现象**：诊断首轮报 `悬停到出画面 ≤400ms —— 1749ms`。

**根因**：悬浮窗是**懒创建**的 —— 第一次 `Show()` 才付出 XAML 解析、布局、
VideoView 原生子窗口创建这一整套开销，实测约 1.7 秒。
设计文档写的是"窗口只创建一次"，但"一次"落在第一次悬停上，等于把最贵的开销
放在了最需要快的时刻。

**修复**：启动后在屏幕外显示一帧再隐藏，把一次性开销提前付掉：

```csharp
NativeWindow.SetPhysicalBounds(window, -20000, -20000, width, height);
window.Show();
window.Hide();
```

**效果**：1749ms → **305ms**。

> 这是个典型的"架构对了但时机错了"的问题：窗口确实只创建一次，
> 但那一次选错了时间点。

### 问题 2：模态对话框卡死无人值守运行

**现象**：诊断跑到音频测试前就再无日志，进程不退出也不报错。

**根因**：未处理异常的兜底处理器弹 `MessageBox`，而 MessageBox 是**模态阻塞**的。
自动化环境里没人点"确定"，进程就永久挂在那里。

**修复**：诊断模式下把异常写进日志而不弹窗：

```csharp
DispatcherUnhandledException += (_, args) =>
{
    DiagnosticsLog.Error("UI 线程未处理异常", args.Exception);
    if (IsDiagnosticMode) { args.Handled = true; return; }   // 不弹窗
    MessageBox.Show(...);
};
```

### 问题 3：主窗口尺寸没按 DPI 钳制，卡片被排到屏幕外

**现象**：悬浮窗定位到 x=1665，看起来像"跑到屏幕外"。

**根因**：主窗口默认 1280×820 **DIP**，在 200% 缩放下发 2560×1640 **物理像素**。
窗口本身超出屏幕，里面的卡片自然也被排到屏幕外，悬浮预览跟着定位到看不见的地方。

**修复**：用 Win32 取物理工作区，再按 `GetDpiForWindow` 的实际 DPI 换成 DIP 后钳制：

```csharp
var scale = NativeWindow.GetDpiScaleForWindow(handle);
var work  = NativeWindow.GetMonitorWorkArea(0, 0);
Width  = Math.Min(Width,  work.Width  / scale);
Height = Math.Min(Height, work.Height / scale);
```

> 顺带一个认知纠正：PowerShell 是 **DPI 非感知**进程，它报告的
> `Screen.Bounds = 1280x800` 是虚拟化后的值，实际面板是 2560×1600。
> 一度让我误判"坐标跑到屏幕外了"。

### 问题 4：崩溃后残留临时文件

**现象**：阶段2 冒烟测试报 `崩溃恢复后无残留临时文件 — .tmp 下 1 个`。

**根因**：取消时 ffmpeg 刚被强杀，**文件句柄尚未释放**，`File.Delete` 抛
`IOException` 被静默吞掉。而任务执行器在恢复中断任务时只重排队、不清临时文件。

**修复**（两处）：
1. `DeleteTemp` 遇到 `IOException` 重试 3 次（每次间隔 80ms）
2. `ImportJobRunner.RunAsync` 启动时清理 `.tmp` —— 让执行器具备自愈能力，
   不再依赖调用方记得清理

## 4. 测试环境干扰的两个发现（不是产品缺陷）

诊断过程中有两次误报，追查后都是**真实鼠标在干扰自动化测试**，而且**恰好反证了功能是好的**：

| 现象 | 真相 |
|---|---|
| "视频播放推进"断言读到 `状态 Stopped` | 鼠标正好停在某张卡片上，触发了新预览把视频顶掉了 —— **悬停功能在真实鼠标下正常工作** |
| "宽限期隐藏"断言失败 | 鼠标移出悬浮窗本体提前触发了宽限隐藏；日志里 `隐藏（原因：宽限期到期）` 本身证明宽限期生效 |

**处理**：诊断模式下屏蔽真实鼠标输入（`_ignoreRealMouseHover`、`IgnoreWindowPointerEvents`），
并把宽限期测试改成先重置状态再测。

> 这是自动化测试的正确姿势：把不可控的外部变量排除掉，
> 否则你会在"功能其实是好的"和"断言失败"之间反复浪费时间。
